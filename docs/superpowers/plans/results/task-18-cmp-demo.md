# Проба оцифровки элементов на реальном снимке CMP (задача 18, шаг 6)

Снимок: `data/cmp/base/cmp_b0013.jpg` (996×1024, фасад в Барселоне, из набора
[CMP Facade Database](https://cmp.felk.cvut.cz/~tylecr1/facade/), см.
`docs/superpowers/plans/results/geometric-core-smoke.md` — задача 17 показала, что
на этом снимке плоскость восстанавливается (доверие 0.658, один из 174 из 378).

Артефакты — рядом, в `docs/superpowers/plans/results/task18-cmp-demo/`:

- `cmp_b0013.json` — выход `facade-digitize`, три размеченных окна;
- `cmp_b0013_rectified.png` — сохранённый выровненный растр (`--save-rectified`);
- `cmp_b0013_rectified_mask.png` — маска охвата рядом с ним.

## Числа в миллиметрах здесь НЕ являются точными

**Масштаб выдуман**, тем же путём, что и в задаче 17: у CMP нет истинного размера
фасада, `scale_source="assumed_floor_height"`, опорная база — 80 % ширины кадра,
которой ПРИПИСАНО 8000 мм. Это видно и в самом выходном файле, а не только в этом
описании — `facade.scale`:

```json
{"source": "assumed_floor_height", "sigma_rel": 0.05, "meets_tolerance": false}
```

`sigma_rel = 0.05` (5 %) и `meets_tolerance = false` — ровно то, что спецификация,
п. 6.3, сама признаёт недостижимым для этого источника; величина не подогнана под
проверку, она получилась сама. Поэтому `size_mm.width ≈ 900 мм` у размеченных окон —
это демонстрация того, что цепочка «клик оператора → миллиметры → σ» работает
целиком, а не измерение реального окна. Демонстрируется работа конвейера, не
точность (это прямо оговорено заданием шага 6).

## Разметка

Три окна одного вертикального ряда (второй столбец слева), координаты взяты из
эталонной XML-разметки набора CMP (`cmp_b0013.xml`, объекты `labelname=window`,
переведены из долей кадра в пиксели) — то есть это не мои визуальные оценки на
глаз, а координаты, независимо размеченные авторами набора для другой задачи
(детекции), использованные здесь как if оператор указал те же четыре угла:

```jsonc
[
  {"class": "window", "mounting": "embedded", "edge_type": "unknown",
   "corners_px": [[252.9, 167.6], [343.4, 167.6], [343.4, 103.8], [252.9, 103.8]]},
  {"class": "window", "mounting": "embedded", "edge_type": "unknown",
   "corners_px": [[252.9, 324.9], [343.4, 324.9], [343.4, 262.2], [252.9, 262.2]]},
  {"class": "window", "mounting": "embedded", "edge_type": "unknown",
   "corners_px": [[251.9, 539.8], [343.4, 539.8], [343.4, 476.0], [251.9, 476.0]]}
]
```

`edge_type = "unknown"` — честно: по одному снимку из интернета нельзя утверждать,
что кромка окна лежит в плоскости стены, а не на выступающем наличнике
(спецификация, п. 5.3). `reveal` не размечен: на этом разрешении (996×1024,
исходный кадр CMP уже сжат относительно оригинала) грань откоса неразличима, а
демонстрировать `recess` на неразличимой грани значило бы выдумывать входные
данные, а не показывать конвейер — синтетика (`tests/test_elements.py`) для этого
и существует, там глубина известна точно.

## Команда

```
facade-digitize data/cmp/base/cmp_b0013.jpg \
  --raster-mm-per-px 10.0402 \
  --origin-px 99.6 921.6 \
  --span-px 99.6 921.6 896.4 921.6 \
  --span-mm 8000.0 \
  --scale-source assumed_floor_height \
  --marks <marks.json из блока выше> \
  --save-rectified \
  --out-dir docs/superpowers/plans/results/task18-cmp-demo
```

## Результат

```
cmp_b0013.jpg: docs\...\task18-cmp-demo\cmp_b0013.json (reject)
```

Вердикт `reject` — из-за разрешения (`gsd_max_mm_px` посчитан от выдуманного
масштаба и превышает порог 5 мм/px), не из-за элементов; это тот же эффект, что
задача 17 уже объяснила для всего набора CMP. Три элемента в `elements`:

| id | width, мм | height, мм | σ_width | σ_height | θ(x,y), ° | meets_tolerance |
|---|---:|---:|---:|---:|---:|---|
| w_000 | 907.7 | 639.6 | 82.9 | 76.4 | 28.2 | false |
| w_001 | 907.8 | 629.5 | 80.6 | 73.7 | 20.4 | false |
| w_002 | 917.7 | 639.8 | 79.7 | 72.6 | 14.2 | false |

Наблюдения, все — свойства выдуманного масштаба и реального ракурса, а не дефект:

- `sigma_width`/`sigma_height` доминированы слагаемым масштаба (`width · sigma_rel`,
  `sigma_rel = 5 %` даёт ≈ 45 мм из ≈ 80 мм) — ожидаемо для источника, который сама
  спецификация не считает годным;
- `θ(x, y)` разное у трёх окон одного столбца (28.2° → 20.4° → 14.2°, сверху вниз) —
  элементы дальше от опорной точки камеры дают больший угол визирования, ровно та
  зависимость от СОБСТВЕННОЙ точки элемента, которую требует спецификация, п. 2.1
  (не θ_cam и не сводка по кадру, см. `ImageRecord.theta_cam_deg` ниже);
- `meets_tolerance = false` у всех трёх — ожидаемо: допуск п. 2.2 (1σ ≤ 10 мм)
  недостижим при `sigma_rel = 5 %` практически на любом габарите;
- `recess: null` — `reveal` не размечен (см. выше), поэтому глубина не вычислялась,
  а не «не найдена».

Для сравнения — поза камеры и наклон этого же кадра (задача 17 в действии, теперь
рядом с элементами, а не изолированно):

```json
"rectification": {"method": "vanishing_points", "confidence": 0.658, "residual_px": 0.330},
"pose_to_facade": {"cx": 4006.6, "cy": 4102.5, "cz": 7963.3, "units": "mm"}
```

## Растр

`cmp_b0013_rectified.png` (999×1027) — фронтальный вид фасада; охват (маска)
99.4 % кадра, как и следует ожидать от снимка CMP, который уже близок к

бесконечности»). Растр сохранён СПЕЦИАЛЬНО для показа оператору и не был
использован для измерения: три окна размечены по координатам в ИСХОДНОМ снимке
(спецификация, п. 6.5; докстринг `pipeline/elements.py`).
